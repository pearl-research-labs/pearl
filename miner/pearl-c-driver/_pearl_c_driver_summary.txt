INTERPRETATION
==============
The C skeleton reaches the GEMM-only kernel ceiling on sm_89 W19R-prod
(~92 TOPS), matching CLAUDE.md memo "GEMM-only 92.42 TOPS in unified
harness". This is the upper bound for the per-nonce loop if you ELIMINATE
all per-nonce Python overhead AND all per-nonce host-side work
(apply_sparse_noise).

The Python pipeline runs at 25 effective TOPS because:
  - GIL + asyncio + dict lookups per nonce  [Python overhead]
  - apply_sparse_noise launched per-nonce   [kernel work; still GPU]
  - GEMM launched per-nonce                  [kernel work; dominant cost]

Going from 25 to 92 TOPS requires the C driver to subsume both:
  1. Per-nonce Python overhead  [eliminated by this skeleton]
  2. Per-nonce apply_sparse_noise dispatch from C [next phase]

CUDA Graph mode [256 GEMMs captured as one graph] gives virtually identical
throughput as the launch loop, so the kernel is compute-bound, not launch-bound,
at this shape. The 3.71x gap to Python is therefore entirely GIL/asyncio
overhead, not cuLaunchKernel cost. This is consistent with the v2 orchestrator's
profile [Python ~3 ms/nonce of host time on top of ~1.4 ms/GEMM].

RECOMMENDATION
==============
CONTINUE. The skeleton demonstrates a 3.71x effective-TOPS headroom
[25 -> 92] is achievable from kernel ceiling alone. Combined with
W19R-2 Approach D [projecting +90 TOPS independent of Python overhead],
the path to 100+ effective TOPS is two parallel workstreams:

  Track A [this work]:        C driver replacing Python orchestration
                              -> 25 -> 70-90 effective TOPS in 2-3 weeks.
  Track B [Approach D agent]: Stage 3->4 prologue fusion
                              -> +12-20 TOPS independent of orchestrator.

Both tracks land us at 100 TOPS end-to-end. Track A also unblocks
W20+ kernels that require sub-millisecond per-nonce dispatch budgets
that Python cannot meet.

CAVEATS
=======
- Bench drives pow_target=0 so no host-signal probe; production needs
  host_signal_sync + host_signal_header_pinned (cudaHostAlloc) and the
  driver must spin-check the pinned status word every iteration.
- LD_PRELOAD libpython is a load-time workaround; switching to ctypes
  dlopen on demand or stripping the .so DT_NEEDED would be cleaner.
- This skeleton compiles inside the pearl-build-hostnet container that
  also builds pearl-gemm. Building outside the container requires
  installing CUDA 12.x + CUTLASS headers + a libpython.
